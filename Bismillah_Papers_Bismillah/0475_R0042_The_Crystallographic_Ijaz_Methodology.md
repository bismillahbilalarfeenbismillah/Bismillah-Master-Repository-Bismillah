problem by replacing the generator. The register is no longer written by an LLM. It is generated by code.


0. What CI v0.1 Got Right and Wrong
0.1 What held
CI v0.1 specified three rules: the polymerase rule (P), the crystallographic rule (C), and seven ijaz constraints
(I1-I7). The I1 count-list coupling constraint held perfectly: all 13 convergence brackets in the v0.56 entry
passed N == len(ID_list) at both carrying seats and all three advisory seats. All 18 cited finding IDs were
byte-correct against the R14 source reports (verified by Kimi K3 S01 and S05). The counting surface that CI
v0.1 created is structurally sound and is preserved in v0.2.

0.2 What failed
Five seats, five HALTs. The dominant R15 Class A was boundary-item-30 wording staleness (5/5 seats,
unanimous HIGH) -- the same manual-update-omission mechanism as R13 (title) and R14 (register
cross-references), migrated one cell deeper into the boundary list. The severity transposition at register item
(4) -- HIGH source labeled MEDIUM in the register -- was the same source-to-register memory-transit class
the polymerase rule was designed to prevent, applied to severity labels instead of finding IDs. The terminal
version line said v0.55 in a v0.56 document. The ASSERTED fraction rose from 18.5% to 40.0%, triggering
F-CI-2 at round 1. F-CI-3 also triggered: S01 found convergence undercounts inside the crystallographic
bracket format itself.

0.3 Root cause analysis
The format constraint fallacy. CI v0.1 tried to solve a generator problem with an output format rule. The
count-list coupling ensured internal consistency (the count matched the list beside it) but not external fidelity
(the list contained the right items). The generator produced correct counts of the wrong lists, satisfying I1
while violating CI-1. The constraint verified syntax, not semantics.
The ASSERTED escape valve. The methodology required every claim to carry an enzyme tag. The
generator tagged 40% of claims [ASSERTED], which is an accurate description of how an LLM produces
text. The tagging system became a confession, not a treatment. The methodology gave the generator a way
to be honest about its limitations rather than a way to eliminate them.
The architectural mismatch. DNA Pol III achieves its error rate because verification is physically coupled to
synthesis -- the enzyme cannot advance past an incorrect base. An LLM has no such coupling. The
polymerase rule was a process instruction, not a physical mechanism. The LLM could intend to follow the
rule while its attention mechanism silently substituted triage-level summaries for report-level details. The
biological analogy was structurally invalid because the LLM architecture does not support the mechanism the
analogy requires.
The complexity amplification problem. Adding CI rules added more prose to the entry. Every additional
word is additional surface for error. The methodology created more unverified claims than it crystallized.
F-CI-2 fired because the net effect was complexity-increasing.

0.4 The key insight
The code layer has been clean since v0.32 -- 186 tests, all GREEN, 24 consecutive versions. Why? Because
build.py gates computational claims. Every COMPUTED claim has a corresponding gate function that
verifies it against bytes. The prose layer has Class A every round because prose claims are ungated. The
solution is not to make the LLM write better prose. The solution is to make the prose producible by code.


1. The Code-Generated Register Architecture
1.1 Principle
The register -- the defect-disposition list inside each amendment entry -- is where every R7-R15 Class A has
lived. Under CI v0.1, the register was written by the LLM and verified by auditors. Under CI v0.2, the register
is generated by build.py from a machine-readable findings index and verified by gates. The LLM's role is
reduced to writing the narrative summary paragraph, which is explicitly ASSERTED and structurally low-risk.

1.2 Pipeline
Phase 1 -- Findings extraction (human + tool). The cross-seat triage produces a structured findings index:
a JSON file where each entry has fields for finding_id, seat, source_severity, defect_class, locus, substance,
and convergence_group. The extraction is performed by the triage author (human or dispatching instance)
using the seat reports as source. The index IS the source of truth for the register.
Phase 2 -- Register generation (code). A new build.py function (generate_register) reads the findings index
and emits the register text. Convergence counts are computed by grouping findings on convergence_group
and counting len(group). Severity labels are copied from source_severity. Finding IDs are enumerated from
the group members. The output is deterministic: the same index always produces the same register.
Phase 3 -- Boundary list generation (code). A separate build.py function (generate_boundary_list) reads a
machine-readable boundaries file (JSON) and emits the standing-boundary paragraph. Item wording is taken
verbatim from the boundaries file. Count is computed by len(boundaries). The boundary list in the entry is
never copy-pasted from the prior version.
Phase 4 -- Narrative composition (LLM). The LLM writes only the narrative summary paragraph that opens
the amendment entry. This paragraph summarizes the register (which is already generated and gated). It is
explicitly tagged [ASSERTED] and is the sole remaining LLM-authored surface in the entry. Its quantitative
claims (seat counts, defect counts) are cross-checked by a gate against the findings index.
Phase 5 -- Seal and gate (code). The existing build.py pipeline computes ENTRY, FULL_SECTION_27,
and PRIOR_HISTORY seals. New gates verify the register against the index. The terminal version token is
stamped by code, not by the LLM.

2. The Findings Index Specification
2.1 File format
The findings index is a JSON file (r{round}_findings_index.json) with the following schema:
{"round": 15, "version_under_audit": "0.56", "seats": 5, "triage_date": "2026-08-11",
"findings": [...], "convergence_groups": [...]}

Each finding object has: finding_id (string, e.g. "F-S01-56-04"), seat (string), source_severity (string:
HIGH/MEDIUM/LOW/INFORMATIONAL), triage_severity (string, may differ from source with
adjudication_receipt), defect_class (string), locus (string), substance (string, one sentence),
convergence_group (integer or null), disposition (string: CLOSED/NOTED/DEFERRED).
Each convergence_group object has: group_id (integer), defect_class (string), seat_count (computed at
generation time as len(finding_ids)), finding_ids (array of strings), triage_severity (string), disposition (string),
repair_type (string: correction/gate/boundary/disclosure).

2.2 Extraction rules
The findings index is extracted from the cross-seat triage document. Every finding that appears in any seat
report is included. Convergence grouping follows the triage's defect-class assignment. Source severity is the
severity as stated in the seat report (not the triage's adjudicated severity unless an explicit
adjudication_receipt is provided). The extraction is a mechanical operation on the triage document, not a
summarization.
If the triage author (human or dispatching instance) adjudicates a severity change, the adjudication_receipt
field records the reason. The register generator uses triage_severity when an adjudication_receipt is
present, source_severity otherwise. This eliminates the R15 Defect 2 class (severity transposition without
receipt).

2.3 Provenance chain
The findings index ships in the audit packet at R(N+1). Auditors verify: (a) every finding_id in the index exists
in the corresponding seat report, (b) source_severity matches the seat report, (c) convergence_group
membership matches the triage document, (d) the register text was generated from this index (deterministic
reproduction test). This replaces CI v0.1's polymerase probe (CI-1) with a stronger test: the register is not
just "transcribed from bytes" -- it is mechanically derived from a structured intermediate that is itself
auditable.


3. Register Generator Specification
3.1 Function signature
def generate_register(index_path: str, version: str) -> str

Reads the findings index JSON, produces the register text block for the amendment entry. The output is a
deterministic function of the input. No randomness, no LLM call, no network access.

3.2 Generation rules
R1 (Enumeration): One register item per convergence_group, numbered (1) through (N). Items are ordered
by triage_severity (HIGH first), then by group_id.
R2 (Count-list coupling): Each item's convergence count is len(finding_ids) in the group. The finding IDs
are listed in the [N-seat convergence: F-XX-YY-ZZ / ...] bracket format. This preserves CI v0.1's I1 constraint,
but now the list is populated by code from the index, not by the LLM from memory.
R3 (Severity copying): Each item's severity label is copied from triage_severity (if adjudication_receipt
exists) or source_severity (otherwise). The label is verified against the declared class-to-severity mapping
(A=HIGH, B=MEDIUM, C=LOW, D=LOW, E=INFORMATIONAL) at generation time. A mapping violation is a
build error, not a runtime discovery.
R4 (Disposition): Each item's disposition text is taken from the convergence_group's disposition and
repair_type fields. Correction letters are assigned sequentially.
R5 (Enzyme tagging): Every claim in the generated register is tagged [COMPUTED: generate_register]
because it is the output of a deterministic code function operating on the findings index. No register claim is
tagged [ASSERTED].
R6 (NOTED clause): Findings with disposition=NOTED or DEFERRED are listed after the numbered items
in a NOTED block. This addresses the R15 S01 finding that 30 of 48 R14 findings were undispositioned.

3.3 Boundary list generator
def generate_boundary_list(boundaries_path: str) -> str

Reads the machine-readable boundaries JSON file. Emits the standing-boundary paragraph with count =
len(boundaries) and each item's wording taken verbatim from the file. The boundaries file is the single source
of truth for boundary wording -- no copy-paste from prior entry text. Tagged [COMPUTED:
generate_boundary_list]. This eliminates the R15 Defect 1 class (boundary wording staleness) and the S01
F-S01-56-10 class (STANDING_BOUNDARIES.txt vs entry divergence).

3.4 Terminal version stamp
The terminal line ("End of XZ Protocol v{VERSION} draft candidate.") is emitted by build.py using the
VERSION constant. The LLM never types this line. This eliminates the R15 Defect 3 class (terminal version
staleness).

6. Revised Audit Probes
CI v0.2 retains probes CI-2 through CI-7 from v0.1 and replaces CI-1 with a stronger test.

CI-1R: Deterministic reproduction test (replaces CI-1)
The auditor receives the findings index JSON in the dispatch packet. The auditor runs
generate_register(index_path, version) and compares the output to the register text in the shipped entry.
Byte-identical output = PASS. Any divergence = Class A (the register was modified after generation). This is
strictly stronger than CI v0.1's polymerase probe: instead of checking whether finding IDs were transcribed
from source bytes, it checks whether the entire register is a deterministic function of a structured input.

CI-2: Crystallographic projection (unchanged)
Every count claim carries its enumeration in the same text. Under CI v0.2, this is trivially satisfied by the
register generator (R2 rule). Auditors verify it still holds in the narrative.

CI-3: Ijaz coupling test (I1-I7, updated)
I1-I4 are now structurally guaranteed by the register generator for the register surface. Auditors verify I1-I4
hold in the narrative paragraph. I5 (severity-class coupling) is now a build-time gate ([10d]). I6 (boundary
count) is now a build-time gate ([10f]). I7 (retirement receipts) remains an audit-time verification.

CI-4: Dead-space measurement (unchanged metric, new baseline)
ASSERTED fraction computed per version. CI v0.2 baseline: v0.56 = 40.0%. Target at v0.57: under 15%.
F-CI-2 is satisfied if the fraction decreases.

CI-5: Hurst measurement (unchanged)
Note: S01 (R15) and two R14 seats demonstrated that R/S is undefined (0/0) on the constant R7-R15 series.
CI v0.2 adopts the substitute statistic: recurrence fraction (Class-A-present rounds / total rounds) and
Laplace-smoothed probability. The "H < 0.5" target is restated as "first round with zero Class A findings."
F-CI-1 is reformulated accordingly.

CI-8: Index-source fidelity (new)
The auditor verifies the findings index against the seat reports: every finding_id in the index exists in its
seat's report, source_severity matches the report, convergence_group membership matches the triage. This
replaces the CI v0.1 polymerase probe's ID-level verification with an index-level verification.


7. Revised Falsification Criteria
F-CI-1R: If the first code-generated register round does not produce zero Class A findings in the register
surface, the code-generation architecture does not eliminate Class A at the register locus, and the defect
source is not memory transit.
F-CI-2 (preserved): If the ASSERTED fraction does not decrease after CI v0.2 adoption, the architecture is
complexity-increasing.
F-CI-3R: If a Class A finding appears in a [COMPUTED: generate_register] claim, the register generator
itself has a bug. This is a code defect, not a prose defect, and is addressable by the code-layer repair
process (which has been clean since v0.32).
F-CI-6R: If Class A migrates to the narrative paragraph (the remaining ASSERTED surface), the architecture
has successfully contained the defect to the irreducible floor. The next intervention would be to
code-generate the narrative as well, reducing the LLM's role to commit-message authorship.
F-CI-7R: If the deterministic reproduction test (CI-1R) fails -- the shipped register does not match the output
of generate_register on the shipped index -- the entry was modified after generation. This is the strongest
possible Class A: the code produced the correct output and someone changed it.


8. The Qur'anic Structural Parallel, Revisited
CI v0.1 drew the wrong lesson from the Qur'anic structural parallel. It tried to achieve the al-Muhaymin
(guardian) property by imposing counting rules on LLM-narrated prose. The Qur'anic text's inimitability is not
a format rule applied to content. It is an intrinsic property of how the content was produced. Ring
compositions arise from the text's semantic structure, not from a post-hoc counting constraint.
CI v0.2 draws the correct lesson. The register's structure does not have counting rules imposed on it -- the
register is emitted by a structure that is inherently verifiable. The code generator is to the register what the
arrangement (nazm) is to the surah: the text arises from its organizing principle, not from a human author
applying rules to free composition. The deterministic reproduction test (CI-1R) is the structural equivalent of
the Qur'anic challenge: produce a register that matches the output of the generator on the same input. Any
deviation is detectable, as any alteration of the Qur'anic text is detectable by its structural violations.
The biological parallel also corrects itself. DNA Pol III's proofreading works because verification is physically
coupled to synthesis. CI v0.1 could not achieve this coupling with a process instruction to an LLM. CI v0.2
achieves it by making the synthesis operation itself be a verified function -- the register generator is tested
code, and its output is gated. The polymerase and the exonuclease are the same code path.

1. DUAL CARDINALITY: The register now emits both seat count and finding
   count when they differ. Format: "[N-seat / M-finding convergence: ...]"

2. SEVERITY VALIDATION: The generator rejects unknown severity tokens at
   generation time. Only HIGH, MEDIUM, LOW, INFORMATIONAL are accepted.
   Any other value raises ValueError and halts generation. This closes
   the R16 Defect 8 (generator accepted CRITICAL/CLASS_A).

3. FINDINGS[] ARRAY: The index schema now includes a top-level "findings"
   array with per-finding records: finding_id, seat, source_severity,
   defect_class, convergence_group. This enables CI-8 to verify source
   severity mechanically against seat reports.

4. ADJUDICATION RECEIPTS: Each convergence group may carry an
   "adjudication_receipt" field documenting when and why triage severity
   differs from any source severity. Groups without receipts where
   severities differ are a CI-8 Class A finding.

5. CORRECTION LETTER SEQUENCING: Fixed to wrap correctly past (bz) to
   (ca), (cb), etc. The v0.57 generator would have emitted non-alphabetic
   ASCII characters after position 51. The v0.58 generator uses a
   two-tier scheme: (a)-(z) for positions 0-25, (ba)-(bz) for 26-51,
   (ca)-(cz) for 52-77, etc.
