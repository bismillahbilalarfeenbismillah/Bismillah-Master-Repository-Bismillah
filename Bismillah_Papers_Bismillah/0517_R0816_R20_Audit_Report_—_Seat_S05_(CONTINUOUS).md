## Findings — six-element format

### F-S05-61-01

**Severity:** HIGH (Class A)
**Locus:** protocol Status; v0.61 register item (1); NOTED register groups; `xz_protocol_register_gen.py` receipt validation and emission logic.

**Substance:** The v0.61 claim that source-severity distribution is now load-bearing and receipt content is validated against the computed distribution is still overbroad. Source distributions are emitted only for numbered CLOSED/SCOPED_OUT items, not NOTED groups. A valid source-severity change in NOTED group 7, accompanied by a correct updated receipt, leaves generated bytes unchanged. Independently, receipt validation is substring-based rather than count-exact.

**Evidence:** Changing one group-7 source from HIGH to MEDIUM and updating the receipt truthfully to `1 HIGH, 1 MEDIUM` is accepted and produces the exact baseline register SHA-256. Changing both group-7 sources HIGH→MEDIUM is also byte-identical. For receipt fidelity, the actual baseline group-7 distribution is `2 HIGH`; replacing its receipt with `12 HIGH source findings; triage severity MEDIUM.` is accepted because the validator merely checks whether character `2` and token `HIGH` occur somewhere in the receipt. Generated bytes remain identical.

**Consequence:** R19 Surface 1 is only partially discharged. M2/M3 closure is real for some CLOSED groups, but the advertised general invariant is false and a stale/false receipt can still authenticate a contradictory source distribution.

**Recommendation:** Emit the computed distribution for every group, including NOTED/DEFERRED groups. Replace free-text substring validation with a structured receipt containing exact `{severity: count}` data and compare structural equality to the computed distribution.

**Falsifier:** Any valid source-distribution mutation must either change generated evidence or fail; a receipt claiming `12 HIGH` must fail against an actual `2 HIGH` distribution.

### F-S05-61-03

**Severity:** HIGH (Class A)
**Locus:** `xz_protocol_register_gen.py` cross-layer validation; `r19_findings_index.json` scalar `findings[].convergence_group`; v0.61 register item (4).

**Substance:** Cross-layer validation now rejects nonexistent group IDs, but it still does not enforce **membership parity** between each finding's scalar `convergence_group` and the group whose `finding_ids` actually contains it. R19 F-S05-60-02 therefore remains only partially discharged.

**Evidence:** Mutating `F-S01-60-01` from scalar `convergence_group: 1` to `2` is accepted because both group IDs exist. The generated register is byte-identical. The generator uses the convergence-group objects for generation and treats the scalar field only as an existence check. By contrast, mutating the same field to `999` correctly fails closed.

**Consequence:** The same finding can simultaneously claim membership in group 2 at the finding layer and be rendered as a group-1 member at the register layer. The schema can be internally contradictory while generation remains GREEN.

**Recommendation:** Require bidirectional parity: for every grouped finding, the scalar group must equal the unique containing group's `group_id`; every group member must point back to that group. If secondary membership is intended, model it explicitly as an array with declared semantics.

**Falsifier:** A valid-but-wrong reassignment `1→2` must fail, not merely an invalid `1→999` reassignment.
