# SHVVP v0.8-rc1 audit-absorption changeset

## Disposition

The v0.7 Seat-A verdict is accepted in full: F-P7-1 and F-P7-2 are HIGH and BLOCKING; F-P7-3 and F-P7-4 are MEDIUM. This candidate changes the route-gate trust architecture and corresponding Section 8 text, while carrying the v0.5 decision and power modules unchanged.

## F-P7-1 - caller-selectable verification key

The `trusted_pubkey` parameter is removed from `route_claims`, `evaluate_gate`, and every verifier path. Three exact Ed25519 public keys are embedded in the manifest envelope: commitment authority, run logger, and pre-run anchor. Every signature verifier references those constants directly. The result object reports only those manifest-bound keys. Tests A1-A8 cover API inspection, rejected keyword override, caller-generated self-signing, and validly signed cross-version, cross-manifest, and cross-component objects.

## F-P7-2 - no genuine pre-run commitment

REALIZED commitments now contain four required layers:

1. a signed pre-run commitment fixing commitment ID, run ID, schema digest, inclusion-rule digest, deterministic genesis, logger key, component/universe/version/manifest bindings, sequence, and UTC time;
2. a separately signed anchor receipt over the pre-run digest, with independent authority, sequence, and UTC time;
3. individually logger-signed append events, each binding the pre-run digest, previous chain hash, contiguous sequence, observation time, and canonical event payload;
4. a commitment-authority-signed close receipt binding the pre-run digest, realized total, sequence range, final chain, and closure time.

Verification rejects a correct-authority close without pre-run/anchor, a caller-completed list signed under the wrong logger, absent or mutated pre-run/anchor material, truncation, reordering, duplicate sequences, broken links, time reversal, post-signature event mutation, count disagreement, and missing append history. Tests B1-B15 execute these paths.

## F-P7-3 - meaningless commitment ID

All signed SEALED and REALIZED payloads contain a unique `commitment_id`. Channel A is indexed by that ID, and the raw record's ID must resolve exactly to the signed object. Aliases and arbitrary nonempty strings reject. Close receipts and append events bind the same pre-run ID and digest. Tests C1-C3 cover unknown, alias, and cross-component IDs.

## F-P7-4 - contradictory denominator prose

The Table 8.2a introduction now says:

> For a SEALED component the count shown is only the minimum floor; the committed cardinality is obtained exclusively from the exact authenticated Channel-A sealed commitment resolved by `commitment_id`, never from the raw record. For a REALIZED component the count shown is only a floor; the denominator is the total derived from the independently anchored, individually signed append history and its bound close receipt.
