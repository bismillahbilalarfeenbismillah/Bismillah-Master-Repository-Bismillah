FIVE-LAYER STRUCTURAL AUDIT ARCHITECTURE -- Reference for R14 Seats
====================================================================

Every finding you produce must be classified under all five models.
This document is your reference. Read it before the audit; consult it
when writing findings.

The five layers answer five questions about every defect:
  WHERE does it live?       -> Model I:   Recursive Fractal Cube
  WHAT kind of claim is it? -> Model II:  Enzyme-Substrate System
  HOW was it (not) verified -> Model III: Replication Fork
  WHO is auditing it?       -> Model IV:  Quantum Orbital
  WHY does it persist?      -> Model V:   Cross-Domain Lens (seat-specific)


MODEL I: RECURSIVE FRACTAL CUBE (WHERE)
---------------------------------------

The protocol is a Menger sponge. At each level, divide the artifact
into 27 analytical cells (3x3x3 grid, three layers deep). Remove the
center cell and 6 face-center cells. Retain 20. The 7 removed cells
are where defects live -- the ungated prose interiors that no gate
checks.

Layer 1 (CLAIMS): 9 cells.
  Rows: current-entry (1), carried-entry (2), standing-property (3).
  Cols: identity (A), count (B), reference (C).

  A1: version/status claims in the current entry
  B1: seat/finding/boundary counts
  C1: finding-ID cross-references
  A2: append-only preservation of historical entries
  B2: historical count consistency
  C2: historical ID provenance
  A3: FB status assertions
  B3: test/code partition claims
  C3: seal/hash chain references

Layer 2 (GATES): 9 cells.
  Same row/col structure, populated by build.py sections.
  A1: [2] version parity, [2e] title, [2f] status provenance
  B1: [9] entry count, [9f] register count, [2h] boundary count
  C1: [9f] finding-ID regex
  A2: [3a] FB digest loci
  B2: [9e] cardinal range
  C2: [3] file digest verification
  A3: [2c] status word
  B3: [5] test execution, [8] pytest
  C3: HISTORY.sha256 seal chain, [9b] PRIOR_HISTORY

Layer 3 (EVIDENCE): 9 cells.
  Byte-verified evidence for each claim.

The 7 REMOVED cells are the face-center interiors of each layer:
these are the prose surfaces that sit between the checked edges.
ALL Class A findings from R7 through R13 lived in these removed
cells. The R14 audit should focus almost entirely here.

Generator levels:
  L0 = the entry-writing process itself
  L1 = the amendment entry text
  L2 = the corrections and body repairs
  L3 = the register dispositions
  L4 = the standing properties (counts, FB status)

A defect at Level N is generated by the process at Level N-1.
If the same defect class appears at L1, L2, L3, and L4, the
generator is at L0 -- no Level 1-4 patch will extinguish it.

v0.55 significance: Four new gates ([2e]-[2h]) moved four previously
removed cells into the retained set. The dead-space fraction should
have decreased. Measure it.

Fractal dimension D = log(20)/log(3) ~ 2.727 for the idealized
sponge. Compute D = log(N_gated)/log(N_total) for v0.55 and compare.

Hurst exponent H of the Class A recurrence (R/S analysis):
  H > 0.5 = persistent (generator still active)
  H < 0.5 = anti-persistent (generator constrained)
  H ~ 0.5 = random
The handoff claims H ~ 1.0 across R7-R13. If R14 is the first
round with zero Class A, does H drop? What does this predict?


MODEL II: ENZYME-SUBSTRATE SYSTEM (WHAT)
-----------------------------------------

Six verification enzyme types. Every tagged claim in the v0.55 entry
is tagged with one of these. The enzyme type determines HOW the claim
was verified (or should have been).

COMPUTED    -- verified by executing a command (pytest, sha256sum, grep,
              build.py section). The tag names the specific command or
              build.py section. Verify: the named command/section exists
              and checks what the tag claims it checks.

DIFF-VERIFIED -- verified by diffing two file versions. The claim
              states what changed from version N-1 to version N.
              Verify: the claimed text exists at the claimed locus on
              shipped bytes.

ENUMERATED -- verified by parsing and counting a list. The tag names
              the count and the list. Verify: the paren-aware
              enumeration of the list yields the declared count.

PROVENANCE -- verified by tracing IDs to source reports. The tag
              names the source. Verify: the cited ID exists in the
              named source (if the source ships) or is internally
              consistent (if it does not).

COUPLED    -- verified by checking co-varying properties. The tag
              names the coupling constraint. Verify: both sides of
              the constraint agree.

EXTERNAL   -- verified against state the producer does not control.
              The tag names the external anchor (Zenodo DOI, carrying-
              seat dispatch manifest). The producer cannot forge this.

The v0.55 entry has: COMPUTED: 10, EXTERNAL: 2, ASSERTED: 5.
ASSERTED fraction: 5/17 = 29.4%.

ASSERTED claims are claims no enzyme can verify because they describe
process (what was done), not state (what the bytes say). An ASSERTED
claim can still be byte-false if it misstates a verifiable fact under
the ASSERTED label. Check every ASSERTED claim for factual accuracy.

STRAND DISCRIMINATION RULE (non-negotiable):
  If prose and bytes disagree, prose is wrong.
  The bytes are the leading strand. Prose is the lagging strand.
  When they diverge, the error is always in the prose.


MODEL III: REPLICATION FORK (HOW)
----------------------------------

The six-phase build pipeline that should produce a clean entry:

Phase 1 (Helicase): Unwind the prior version. Read findings. Write
  corrections with byte-verified quotations.

Phase 2 (Primase): Apply body repairs with DIFF-VERIFIED. Each repair
  names the locus, the old value, and the new value.

Phase 3 (Polymerase): Compose the register. Each register item cites
  finding IDs with PROVENANCE, states convergence counts, and assigns
  dispositions.

Phase 4 (Exonuclease): Enumerate boundaries, counts, EXTERNAL
  anchors. Every count written by computation, not recall.

Phase 5 (Ligase): Compute seals: ENTRY seal, FULL_SECTION_27,
  PRIOR_HISTORY. Compute HISTORY.sha256 and PACKET_SHA256SUMS.

Phase 5b (Terminal recomputation): Re-derive ALL seal-value, count,
  and enumeration literals from the complete document. This phase
  exists because Phase 5's output changes the document, which
  invalidates Phase 4's counts if they were computed on pre-Phase-5
  bytes.

The R13 defects (title version stale, status provenance stale, FB-7b
row stale) were Phase 2 failures -- body repairs that were applied to
derived loci but not to the authoritative loci. The structural cause
is that Phase 2 operates on the producer's mental model of the
document, not on the bytes. The four new gates ([2e]-[2h]) add
Phase 5b-style verification at Phase 2's output loci.

For R14: the question is whether Phase 3 (register composition)
contains the same class of memory-driven error that Phase 2 contained
at R13. Specifically: are the finding-ID cross-references in the
register accurate against the external reports?


MODEL IV: QUANTUM ORBITAL (WHO)
---------------------------------

Four quantum numbers define each seat:
  n  = principal (energy shell): 1=K (baseline), 2=L (structural),
       3=M (cross-domain), 4=N (meta)
  l  = angular momentum (analytical shape): 0=s (uniform), 1=p
       (dual-axis), 2=d (four-lobe), 3=f (seven-lobe)
  ml = magnetic (framework orientation): specific lens within the
       analytical shape
  ms = spin (fresh/continuous): -1/2=fresh, +1/2=continuous

Pauli Exclusion: no two seats share all four quantum numbers.

Aufbau: fill in order of increasing (n+l). Baseline (1s) before
structural (2s/2p) before cross-domain (3s/3p/3d).

Hund's Rule: diversity before depth. Fill all orientations at a
given (n,l) with parallel spin before pairing any orientation.

Shielding: inner shells verified by prior seats reduce the
analytical burden on outer shells. The computational baseline
is shielded -- it has been clean since v0.32.

Your seat's quantum numbers are in your DISPATCH.txt.


MODEL V: CROSS-DOMAIN LENS (WHY)
----------------------------------

The fifth model is seat-specific. It provides the analytical
framework that explains WHY a defect persists or recurs. Your
specific lens is in your LENS_[name].txt file.

The five lenses deployed at R14:

  Differentiator (S01): The ten-layer Differentiator Framework.
    Why does the defect survive ten layers of analytical filtering?

  Fractal Cube (S02): The Recursive Fractal Cube methodology.
    At which recursion level does the generator produce the defect?

  GAN Convergence (S03): Generator-discriminator dynamics.
    Is the generator approaching equilibrium or in a HALT attractor?

  Structural Revelation (S04): Ring composition and ijaz integrity.
    Does the sealed text exhibit the internal coherence it claims?

  Biomedical Fractal (S05): Dead-space measurement and Hurst analysis.
    Is the gate-coverage fraction converging or diverging?


FINDING FORMAT (six elements, all mandatory)

2. Severity:       CRITICAL / HIGH / MEDIUM / LOW
3. Locus:          exact line or section in xz_protocol_v0_55.md
4. Substance:      what is wrong, stated against bytes, with evidence
5. Disposition:    correction required / DISCLOSED / CLEAN / gate improvement
6. Cross-reference: related findings or standing boundaries

PLUS the five-model classification:

  Fractal Cube cell:    e.g., "Layer 1, B1 (count, current entry)"
  Enzyme type:          e.g., "PROVENANCE (finding-ID trace to source)"
  Replication phase:    e.g., "Phase 3 (register composition)"
  Orbital position:     your seat's quantum numbers
  Cross-domain reading: your lens's interpretation of the defect


CLASS TAXONOMY
---------------

Class A: Byte-level error in a sealed claim. HALT-inducing.
Class B: Concealed defect. Misleading tag, correct underlying value.
Class C: Disclosed standing boundary.
Class D: Gate limitation.
Class E: Process observation.

VERDICT
--------

CONDITIONAL PASS (non-HALT): no Class A or Class B findings.
  List any Class C/D/E conditions.
HALT: any Class A or Class B finding exists. State the basis.
