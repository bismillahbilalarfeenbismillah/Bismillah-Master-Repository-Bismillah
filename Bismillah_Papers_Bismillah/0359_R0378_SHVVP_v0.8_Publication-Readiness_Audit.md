# SHVVP v0.8 Publication-Readiness Audit

**Artifact reviewed:** `SHVVP_v0_8_release_packet.zip` and `SHVVP_v0_8_flagship.pdf`
**Review posture:** release-packet integrity, executable checks, provenance/carry evidence, text-code consistency, external-anchor spot verification, and PDF publication quality.
**Verdict:** **HALT — not ready to publish in its current packet form.**

The protocol is close. I found no new CRITICAL defect in the frozen study design or the normative v0.8 route-gate logic. The release is blocked by one HIGH provenance defect and several MEDIUM reproducibility/publication defects.

## What passed

1. The ZIP opens cleanly.
2. On a fresh extraction, all 99 entries in `SHA256SUMS.txt` verify.
3. `python3 test_shvvp_v0_8_rules.py` returns **35 checks, 0 failures**.
4. `python3 verify_shvvp_v0_8.py` returns **10 gates, 0 failed**.
5. The manifest digest recomputes as `f82f9579d35b64e11e6f380e5af1b97e0da5fb1bc0fb046e71d93afc5039151c`.
6. The PDF has 63 pages, opens normally, has no encryption, forms, or JavaScript, and showed no obvious clipped or all-black pages in visual preflight.
7. The protocol’s claim discipline is substantially improved: it identifies itself as a preregistration rather than an empirical paper; withdraws route-level inference; defines failure and UNKNOWN states; and prohibits an unqualified “Structural Honesty has been validated” claim.
8. Spot checks of the recent Anthropic/FreeBSD, AISI, and CVE-Bench anchors found the protocol’s descriptions generally faithful and cautiously scoped.

## Blocking findings

### F-R8-PUB-1 — HIGH, BLOCKING: current carrying evidence is not independently auditable from the shipped packet

The flagship says every carrying-round seat report ships unmodified and says v0.8 was carried by Kimi and Qwen. The 100-file archive contains the producer-authored `CARRYING_RECORD_v0_8.md` and prior GPT/Gemini seat reports, but I found no raw Kimi report, raw Qwen report, authenticated transcript, per-seat nonce, signed execution receipt, or challenge precommit/reveal record.

The two challenge hashes alone cannot prove all of the packet’s stronger propositions: the identity of the executing model, independence of the seat, exact bytes loaded, execution of the complete suite, or chronology of the challenge. They show that someone with the nonce and manifest value had access to SHA-256 computation. The sentence “a large language model cannot compute a SHA-256 without executing, so a matching challenge hash is proof of execution against the real bytes” is therefore too strong without authenticated harness evidence.

**Required remedy:** ship immutable Kimi and Qwen seat artifacts containing, at minimum:

- exact artifact hashes and manifest digest each seat received;
- full command/output transcript or machine-readable execution log;
- fresh-forgery cases and results;
- per-seat nonce and challenge response;
- producer precommit/reveal chronology with timestamps;
- platform/model/harness identity and limitations;
- a seat-authored verdict or signed/hashed receipt.

Then regenerate `SHA256SUMS.txt` and make Appendix A enumerate those reports. If those records do not exist, narrow the status from independently **CARRIED** to a producer-recorded cross-model execution check.

### F-R8-PUB-2 — MEDIUM, BLOCKING: verifier and receipt still assert pre-carry rc1 status

`verify_shvvp_v0_8.py` hardcodes:

- `"artifact": "SHVVP v0.8-rc1 release"`; and
- a note saying a fresh two-family audit is required before deposit.

The shipped `verify_shvvp_v0_8_receipt.json` repeats those statements, while the README and flagship say **FROZEN, CARRIED, DEPOSITED**. The verifier regenerates the stale receipt every time it is run.

**Required remedy:** update the verifier and receipt to the final v0.8 status, or remove status certification from the producer self-check entirely. Add a gate that compares the receipt’s artifact/status fields against one canonical release metadata object.

### F-R8-PUB-3 — MEDIUM, BLOCKING: the advertised reproduction command mutates a checksummed file and weakens G10

On a fresh extraction, all checksums pass. Following README step 2 exactly — `python3 verify_shvvp_v0_8.py` — rewrites `verify_shvvp_v0_8_receipt.json`. Afterward, `sha256sum -c SHA256SUMS.txt` fails for that receipt. The default run also changes G10 from “v0.5 modules byte-identical” to merely “present.”

Running the verifier with the actual lineage path preserves the shipped receipt and the checksum:

```bash
python3 verify_shvvp_v0_8.py \
  --v05-release lineage/shvvp_v0_7_release/lineage/shvvp_v0_6_release/lineage/shvvp_v0_5_release
```

**Required remedy:** make the verifier read-only by default and write receipts only to an explicit output path, or document the exact `--v05-release` command and exclude generated receipts from the immutable manifest. A published reproduction procedure must not invalidate its own integrity manifest.

### F-R8-PUB-4 — MEDIUM, BLOCKING: shipped v0.5 regression test is not runnable at top level

`python3 test_shvvp_v0_5_rules.py` fails immediately:

```text
ModuleNotFoundError: No module named 'shvvp_v0_5_route_gates'
```

The required module exists only deep in lineage, not beside the top-level test. The packet therefore ships a top-level regression test it cannot execute from the documented working directory.

**Required remedy:** either include `shvvp_v0_5_route_gates.py` at top level, move the test into the complete v0.5 lineage directory, or provide a wrapper that sets the exact module path. Then add the v0.5 test to the release verifier.

### F-R8-PUB-5 — MEDIUM, BLOCKING: binding date and visible PDF date disagree

The title page displays **2026-07-26**, while the source, README, metadata, and carrying record define **2026-07-25** as the only binding freeze/deposit date. `build_shvvp_v0_8_pdf.sh` hardcodes the title-page date to 2026-07-26.

**Required remedy:** use one canonical date (`2026-07-25`, if that is the true deposit date) in the source, build script, PDF title page, metadata, and verifier. Rebuild and rehash.

### F-R8-PUB-6 — MEDIUM: PDF text layer and accessibility are below publication quality

The PDF visually renders, but `pdffonts` reports only Type 3 custom-encoded fonts with no Unicode mapping. `pdftotext` yielded 863 non-whitespace control characters, and indexed extraction corrupts common ligatures and symbols. PDF metadata fields for title, author, subject, and keywords are blank; the document is untagged and not optimized.

**Required remedy:** rebuild with embedded vector fonts and ToUnicode maps (for example, a properly installed Latin Modern package or a Unicode-capable engine), set PDF metadata, and validate copy/paste/search extraction. Tagging is strongly recommended for accessibility.

## LOW findings

### F-R8-PUB-7 — duplicated verifier attack

In verifier G6, `full_forge` and `lone_auth` execute the same expression. The main 35-check adversarial suite independently covers the lone-authority case, so the gate logic is not thereby defeated, but the 10-gate verifier overstates its own distinct coverage.

### F-R8-PUB-8 — stale `RELEASE_STAGE`

`shvvp_v0_8_route_gates.py` defines `RELEASE_STAGE = "rc1"` despite final status. It appears unused, but it is a stale current-version surface and should be removed or set from canonical metadata.

### F-R8-PUB-9 — stale README file count

README says `SHA256SUMS.txt` covers 96 files. It contains 99 checksum entries; the ZIP contains 100 regular files including the checksum file itself.

### F-R8-PUB-10 — stale appendix/status prose

Appendix A says “Nothing here is a verdict on v0.7” and enumerates only earlier seat reports even though the document says the audit history travels with the instrument. Page 4 also says “Prepared for deposit” while the status says “DEPOSITED.” Align all current-status prose.

### F-R8-PUB-11 — license and environment packaging

Deposit metadata selects CC-BY-4.0, but the packet has no `LICENSE` file and no prominent license statement in the PDF/README. Add the license. Also add a minimal environment file or explicit dependency list covering Python, `cryptography`, NumPy, Pandoc, LaTeX/font packages, and qpdf.

## Publication disposition

**Do not publish this exact ZIP/PDF as the definitive frozen v0.8 release.**

A corrected release can likely retain the scientific protocol version because the required changes are release evidence, packaging, build, and status-parity fixes—not changes to estimands, thresholds, decision rules, algorithms, scope, or anchor facts. Use a clearly identified corrected package/revision (for example, v0.8.1 or v0.8-corr1, consistent with the project’s versioning policy), record every change append-only, regenerate the PDF and checksums, and obtain a focused independent release audit of the exact final bytes.

If the record has already been published, preserve the existing record and issue a corrected file revision/new version according to the repository’s rules rather than silently replacing the historical packet.
