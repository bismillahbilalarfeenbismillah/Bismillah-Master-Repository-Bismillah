## 1. The signal (what v1.1.4 must close)

The April 29 real-world benchmark surfaced a per-page cost gap that the existing fixture suite did not predict.

| File | Pages | Scan time | ms/page |
|---|---:|---:|---:|
| Bayyinah white paper (existing fixture) | 19 | 256 ms | 13 |
| NIST AI RMF (real, native text) | 48 | 3,575 ms | 74 |
| Tesla 10-K (real, native text) | 144 | 7,142 ms | 50 |
| arXiv LLM survey (real, LaTeX-typeset) | 144 | 47,619 ms | **331** |

The arXiv result is 24x slower per page than the white paper. For a hypothetical agency batch of 1,000 such documents, that is the difference between 5 minutes (existing fixture extrapolation) and 4.6 hours (arXiv class) on a single worker. The horizontal-scaling claim that the cluster scales linearly with cores still holds, but the per-document cost itself is a load-bearing question and not a constant.

A complementary stress signal in flight: 66 dense-PDF benchmark (10x AKIRA Books 01-05, 2x Nausicaa Volumes 1-2). Smoke-test datapoint: Akira Book 01 (13 MB, ~360 pages) scans in 30 seconds and produces 607 findings. At 30,000 ms / 360 pages = 83 ms/page pre-reduction, AKIRA sits in the same per-page cost class as NIST AI RMF (74 ms/page), not in the arXiv dense-LaTeX class (331 ms/page). The absolute scan time differs because of page count, not because of per-page complexity. The post-v1.1.4 graphic-novel projection in section 7.1 is therefore tentative pending Phase 0 measurement of post-reduction per-page cost on AKIRA-class content; whether image-heavy-with-sparse-text content benefits from the cost taxonomy at the native-text reduction rate (~3.5x) or the dense-LaTeX rate (~16x) is the empirical question Phase 0 settles. Full benchmark to be re-run on a chunked driver in parallel with v1.1.4 implementation.

The v1.1.4 ship target is two-dimensional: drive single-scan cost down for dense documents AND lay the horizontal-scale primitives that turn one fast scanner into a cluster.

## 2. The principle

Today's pipeline behaves like a content-walking system. Per-document cost approximates:

```
cost(document) ≈ Σ_mechanism (mechanism_cost × content_density)
```

This is the inverse of load-bearing. As the document grows denser, every mechanism pays the density tax. The 47-second arXiv result is the natural consequence.

A load-bearing architecture pays the density tax exactly once per kind of structural address, never per mechanism, and never re-walks content already walked. Stated as the v1.1.4 invariant:

> Walk the document once. Build the structural address index. Run mechanisms against the index, not against the content.

This is the operational shape of Escape A applied at the document level: verification by structural address, not by content re-derivation. The same property that lets the system stay deterministic across millions of documents also lets the index amortize the parse cost across mechanisms.

## 3. Cost taxonomy

The existing layer split (zahir / batin / routing) is a semantic taxonomy: it classifies mechanisms by what kind of concealment they detect. v1.1.4 introduces an orthogonal cost taxonomy: it classifies mechanisms by what kind of work they require. Cost taxonomy is independent of layer; both stay assigned per mechanism.

### Cost class A: structural address, O(1) per address

Mechanisms that consult a single field of the catalog, /Info, /AA, /OpenAction, /Names, /OCProperties, or the trailer. Look at one location, return a verdict.

Examples from the registry: `javascript`, `openaction`, `additional_actions`, `launch_action`, `metadata_anomaly`, `hidden_ocg`, `embedded_file`, `extension_mismatch`, `duplicate_keys`, `pdf_trailer_analyzer`.

Cost: tiny and constant in document size. Milliseconds on a 1,000-page document.

### Cost class B: indexed content walk, O(content) shared across mechanisms

Mechanisms that need to inspect every content stream, font dictionary, or annotation. Today each such mechanism walks independently. Under v1.1.4 they read from a single shared content index built on the first pass.

Examples: `zero_width_chars`, `bidi_control`, `tag_chars`, `homoglyph`, `mathematical_alphanumeric`, `invisible_render_mode`, `white_on_white_text`, `microscopic_font`, `tounicode_anomaly`, `pdf_off_page_text`, `pdf_hidden_text_annotation`, `pdf_metadata_analyzer`.

Cost today: O(mechanism_count × content). Cost after v1.1.4: O(content) for the index, O(addresses) for each mechanism evaluation.

### Cost class C: cross-correlation, O(content^2) worst case, bounded in practice

Mechanisms that look for relationships between content elements. `overlapping_text` (two spans share 98% of bounding box) is the canonical example. `cross_modal_correlation` if it exists.

Cost today: pairwise comparison over content elements. Cost after v1.1.4: bounded by spatial indexing (R-tree or grid) so the comparison is only over neighbors.

### Cost class D: full-document re-parse, genuinely O(file size)

Mechanisms that need a second parse pass with a different parser configuration. `incremental_update` (count `%%EOF` markers in raw bytes) is the canonical example.

Cost: cannot be reduced below one byte-scan of the file. But there is exactly one of these per document, not 155.

### Distribution of the 159 mechanisms (v1.1.3 ship state, preliminary, validate via profiling)

- Cost class A: 60-80 mechanisms (the bulk of the registry)
- Cost class B: 50-70 mechanisms
- Cost class C: 5-15 mechanisms
- Cost class D: 3-8 mechanisms

Validating this distribution is the v1.1.4 phase 0 deliverable. Pinned in `domain/cost_classes.py` parallel to `domain/config.py`, with an import-time assertion that every mechanism in the registry has a cost class assigned.

## 4. The redesigned scan loop

```
scan(document):
    # Pass 0: format routing (cost class A, runs always)
    if format_routing_divergence(document):
        return mughlaq_verdict()

    # Pass 1: structural-address probe (cost class A, runs always)
    addr_findings = run_address_mechanisms(document)
    if any_tier_1_or_2_in(addr_findings) and early_termination_enabled:
        # Document already failed at structural address. Skip the
        # expensive passes. Verdict is mukhfi or munafiq based on
        # structural address alone. Forensic mode runs all passes.
        return verdict(addr_findings, early_termination=True)

    # Pass 2: build the content index (cost class B foundation, run once)
    index = build_content_index(document)

    # Pass 3: indexed mechanisms (cost class B, run against index)
    content_findings = run_indexed_mechanisms(index)

    # Pass 4: cross-correlation (cost class C, run if pass 3 produced
    #         relevant addresses; spatial-indexed for bounded cost)
    correlation_findings = run_correlation_mechanisms(index, content_findings)

    # Pass 5: full re-parse (cost class D, run once total)
    reparse_findings = run_reparse_mechanisms(document)

    return verdict(addr_findings + content_findings + correlation_findings + reparse_findings)
```

### Production mode vs forensic mode

The two operating modes are exposed via a `mode=production|forensic` query parameter on the `/scan` endpoint, defaulting to production for the public API and to forensic for the internal diagnostic suite.

- **Production mode:** `early_termination=True` plus a 60-second per-scan timeout. The scanner returns at the earliest verdict that satisfies the tier discipline; documents that fail at structural address (Pass 1) skip Passes 2-5 entirely. This is the inline-middleware shape: low-latency verdict for the caller, structural evidence preserved on every Tier 1+ finding, full diagnostic available on demand by re-submitting under forensic mode.
- **Forensic mode:** `early_termination=False` plus a 5-minute per-scan timeout. Every pass runs to completion regardless of earlier findings. This is the operator-investigation shape: a complete picture of every concealment surface in the document, used for adversarial-gauntlet validation, post-incident analysis, and any case where the first finding is not the only finding.

The byte-parity invariant on `IntegrityReport.to_dict()` holds under forensic mode (the merged report is byte-identical to today's production scan). Production mode produces a strict subset of forensic findings: the Pass 1 results, plus any later passes that ran before early termination fired. The two modes are not free of each other; a customer evaluating one mode against the other gets exactly the difference Pass 1 chose to short-circuit.

### What this preserves

1. **Coverage.** Every mechanism still runs on every document that needs it, when forensic mode is enabled. Production mode trades early termination for latency at known cost.
2. **Verdict equivalence.** For any document that today produces verdict X, the redesign produces the same X under forensic mode. The byte-parity invariant on `IntegrityReport.to_dict()` holds.
3. **Tier discipline.** Tier 1, 2, 3 ordering is preserved. The cost classes are orthogonal to the tier classes.

### What this changes

4. **Cost.** The bulk of mechanisms now pay O(addresses) instead of O(content). The arXiv 47-second result should drop into the 1-3 second range. The 144-page Tesla 10-K should drop into the sub-second range. Validate against the post-implementation benchmark.

## 5. The content index

A single read of the document produces:

- **Span list.** Every text span with (page, bbox, render_mode, color, font_id, glyph_codes, unicode_text).
- **Font table.** Every font with (id, encoding, ToUnicode CMap entries).
- **Annotation list.** Every annotation with (page, type, bbox, /F flags, /Contents).
- **Catalog summary.** /OpenAction, /AA, /Names children, /OCProperties /D /OFF, /Info, XMP stream pointer.
- **Trailer summary.** %%EOF positions, byte ranges of incremental updates.
- **Object graph summary.** /XObject inventory, embedded file inventory, /Launch action inventory.

Mechanisms read from the index. Most never touch the document directly again.

The index is per-scan; it is built at the start and discarded at the end. It does not need to persist across scans (each document has its own index). It is not a shared corpus-level structure.

The migration shape preserves backward compatibility: ScanService builds the index and passes it to each analyzer through a new optional parameter. Analyzers fall back to their existing self-walk if the index is None. This lets the migration ship per-mechanism without breaking the byte-parity invariant or the existing test suite.

## 6. Horizontal scale: from one fast scanner to a cluster

The v1.1.4 cost-taxonomy work makes a single scanner fast. Production deployments need many scanners. This section adapts the stateless-replication and hot-path / cold-path concepts from the prior architecture review and pre-registers them as v1.1.4 deliverables.

### 6.1 Stateless worker pool

Each scanner instance is stateless. It loads the mechanism registry at startup, accepts scan requests, processes each request independently, and returns the verdict. No file is stored. No session exists. No state is shared between requests or between instances.

Architecture: N scanner workers behind a load balancer. Each instance is identical. Each runs the same scanner version with the same registry. Adding instances adds capacity linearly. Removing instances reduces capacity linearly. There is no coordination overhead because there is nothing to coordinate.

Workers are processes, not threads, to avoid the GIL on pymupdf-heavy operations. Process-per-worker with worker recycle every N scans (memory hygiene; PDF parsing is a known source of slow accumulation in long-lived processes).

### 6.2 Queue layer (async API)

A queue decouples submission from execution. The current synchronous `/scan` endpoint stays for the live demo and small-volume API users. Production batch deployments use:

- `POST /scans` → submits one or more files, returns `job_id`.
- `GET /scans/:id` → returns status (queued, running, done, failed) and result if ready.
- `POST /scans:batch` → up to N files in one submission. Optional callback URL for push notification on completion.

Implementation: Redis + RQ for the v1.1.4 first cut (single-cluster, low operational complexity). AWS SQS or Cloudflare Queues for v1.2 multi-region. Idempotency key on file SHA-256 + scanner version: re-submissions of the same content under the same version return the cached result without re-scanning.

Retries with exponential backoff for transient errors (file system, OOM, timeout). Hard timeout per scan (configurable; default 5 minutes for forensic mode, 60 seconds for production mode) so a pathological document never blocks a worker indefinitely.

### 6.3 Result store and deduplication

IntegrityReport JSON to object storage (S3, R2, or equivalent). Database index on (file SHA-256, scanner version, scan timestamp, verdict) for query.

Result tiering: hot (last 7 days, on hot storage), warm (last 90 days), cold (archive). Lifecycle policy on the bucket so storage cost stays bounded regardless of throughput.

Deduplication: same file SHA-256 + same scanner version returns a cached IntegrityReport without invoking the analyzer pipeline. This is exact, not similarity-based. A different scanner version invalidates the cache for that file (the registry has changed; the verdict may have changed).

### 6.4 Hot path / cold path separation

The detection path is the hot path. CPU-only. Returns verdict + structural evidence. Fast, deterministic, scales horizontally.

The explanation path is the cold path. Separate service. Takes verdict + evidence and generates a human-readable narrative. May use ML (LLM, embeddings, learned representations). Runs on different compute, with different scaling characteristics.

The two paths never share compute on the critical path. The hot path returns the verdict to the caller before the explanation is generated. The explanation arrives in the dashboard asynchronously. The hot path's determinism is preserved because no neural component sits on it.

For v1.1.4 the explanation layer is template-based (deterministic, CPU-only). For v1.3 the explanation layer can be ML-based without affecting the hot path's determinism.

### 6.5 Capacity numbers (Phase 0 deliverable, not pre-registered)

The v1 draft of this plan inherited a capacity table from the prior architecture review that assumed a pre-v1.1.4 per-document cost structure (roughly 5-18 seconds per mixed-density doc). That cost structure is inconsistent with the post-v1.1.4 SLAs in section 7.1, which target sub-second native text and ~3 seconds per dense LaTeX document. Cross-checking the original 64-worker × 16-core enterprise tier at 5M docs/day required 17.7 ms per doc on a single core, which contradicts every SLA in this plan. The table was inherited, not re-derived.

This revision removes the inherited table and replaces it with a Phase 0 derivation note. Capacity numbers will be pinned in the v1.1.4 closure REPORT.md after the cost-taxonomy validation in Phase 0 produces measured per-core E[doc_time] across the four density classes. Until then, the externally-publishable claim is "linearly scalable on stateless workers; per-core throughput pre-registered in section 7.1; cluster capacity follows from N_cores / E[doc_time] under the published mix ratio."

**Mix-ratio assumption (pre-registered for the Phase 0 derivation):**
- 50% synthesized
- 30% native text
- 15% dense LaTeX
- 5% graphic-novel

Single-core E[doc_time] under this mix at post-v1.1.4 P50 targets: ~1,275 ms (weighted average of section 7.1 P50s). Realistic E[doc_time] including queue, I/O, and variance overhead: 1,600-1,900 ms (to be measured, not asserted). Cluster throughput on N cores ≈ N / E[doc_time]. The capacity table to be published in v1.1.4 closure REPORT.md replaces this projection with measured numbers.

**Customer-specific throughput** at deployment time follows from `N_cores / Σ(f_class × P50_class)` over the four density classes, where `f_class` is the customer's measured fraction of each class in their corpus. The 50/30/15/5 mix above is the default for marketing claims; it is not the operational ceiling. A hospital running an EHR document corpus might be 80/15/5/0 (synthesized-heavy, much higher throughput). A research-grant reviewer might be 10/20/60/10 (dense-LaTeX-heavy, much lower throughput). Phase 0 produces per-class measurements, which lets customers compute their own expected throughput against their own mix without depending on the marketing default.

**Unit economics:** TBD post-Phase 0. The v1 draft's "$0.0001 per document" figure was a function of the inherited capacity table and is removed from this revision pending validated cost structure. The marginal cost claim ("CPU-only, no GPU on the detection path") survives because it follows from the architecture, not from a specific throughput number.

### 6.6 Drift register (self-monitoring at scale)

Standing Principle: the scanner is subject to its own discipline. The scanner monitors itself for the same kind of drift it detects in documents.

Architecture: a `DRIFT_REGISTER.md` file (or database table at scale) records every version transition of the scanner: mechanism count, ZAHIR/BATIN split, test count, registry hash (SHA-256 of the serialized registry), and findings-on-known-fixtures hash (SHA-256 of concatenated verdicts on the adversarial gauntlet fixtures).

At cluster scale, the drift register runs as a periodic health check: every N minutes, each worker scans a known fixture (a small adversarial PDF) and compares the verdict against the expected value pinned in the drift register. If the verdict differs, the worker is flagged as drifted and removed from the load-balancer pool until investigated.

This is the scanner applying its own detection discipline to itself. It is also the operational mechanism that catches dependency drift, environment drift, and silent-corruption issues at production scale.

## 7. Pre-registered SLAs and falsifiable perf regression suite

Pre-registration discipline applied to performance, in the same shape v1.1.3 applied to mechanism counts.

### 7.1 SLAs (pinned before optimization, validated post-implementation)

Per-document scan time targets, P50 / P95 / P99, at three workload-density classes:

| Density class | Representative fixture | P50 target | P95 target | P99 target |
|---|---|---:|---:|---:|
| Synthesized (existing fixtures) | white paper, 19 pages | 250 ms | 500 ms | 1,000 ms |
| Native text (real-world typical) | NIST AI RMF, 48 pages | 1,000 ms | 2,500 ms | 5,000 ms |
| Dense LaTeX / typeset | arXiv survey, 144 pages | 3,000 ms | 6,000 ms | 12,000 ms |
| Graphic novel (worst-case)* | AKIRA Book 01, ~360 pages | 8,000 ms | 15,000 ms | 30,000 ms |

*Graphic-novel row tentative pending Phase 0 measurement. Pre-reduction AKIRA per-page cost is 83 ms/page (native-text class, not dense-LaTeX class). Post-v1.1.4 cost depends on whether image-heavy content with sparse text reduces at the native-text rate (~3.5x, projecting ~24 ms/page × 360 = 8,600 ms) or closer to the dense-LaTeX rate (~16x, projecting ~5 ms/page × 360 = 1,800 ms). The 8,000 ms P50 is the conservative upper-bound projection. Phase 0 may revise the row downward; the 150% trigger applies once measured numbers replace the projection.

If any post-implementation P50/P95/P99 exceeds 150% of its target, the v1.1.4 plan re-opens for review before merge. Same 150% trigger as the v1.1.3 LOC ceilings.

### 7.2 Cluster-level throughput targets

Throughput on N cores is N / E[doc_time], where E[doc_time] is dominated by the per-class P50 with a tail contribution from P95+. The targets below are jointly satisfiable with section 7.1 under the stated P95-frequency assumption. The relationship is `E[doc_time] ≈ (1-f) × P50 + f × P95` for two-point approximation, where f is the fraction of documents falling at or above P95 latency. Throughput drops sharply when f rises; the targets are calibrated to hold under realistic variance, not under the optimistic assumption that every core delivers exactly P50.

| Workload | Target throughput on 16-core single instance | Realistic at P95 frequency |
|---|---|---|
| Synthesized | ≥ 48 docs/sec | ≤ 25% |
| Native text | ≥ 12 docs/sec | ≤ 20% |
| Dense LaTeX | ≥ 4 docs/sec | ≤ 25% |
| Graphic novel | ≥ 2 docs/sec | tight; validate post-implementation |

The v1 draft of this plan stated higher throughput numbers (≥60 / ≥15 / ≥5 / ≥2) that were jointly satisfiable with section 7.1 only at exact-P50 delivery on every core. That conflated optimal cluster utilization with a pre-registered SLA. The numbers above are the realistic claim. Optimal cluster utilization on a saturated cluster with very low P95-frequency workloads can exceed these; that is upside, not the commitment.

Linear scaling claim: 16-instance cluster delivers ≥ 16x single-instance throughput within 5%. Validated by a load test at 16 instances with each density class.

### 7.3 Perf regression test suite (CI-enforced)

A small fixture suite (the four representative documents above, plus the synthesized Bayyinah white paper) with wall-clock asserts. Threshold permissive (3x current target) so CI does not flake on shared runners. Hard fail if any fixture's median wall-clock exceeds 3x its target across 5 runs.

This suite runs on every PR. A PR that breaks performance gets a red CI signal before merge. Same falsifiability shape as the v1.1.3 mechanism-count assertions.

## 8. Migration path (5 phases, 3 weeks)

### Phase 0: validate the cost taxonomy (1 day)

cProfile the arXiv scan. Confirm the 47 seconds breaks down approximately along cost classes A/B/C/D. Assign every one of the 159 mechanisms to a cost class. Commit the assignment as `domain/cost_classes.py` next to `domain/config.py` with an import-time assertion that every registered mechanism has a cost class.

### Phase 1: build the index, leave analyzers untouched (2-3 days)

Add `ContentIndex` to `domain/`. Build it in `ScanService` before analyzers run. Pass it to analyzers but do not require they use it. No verdict change, no perf change. This is plumbing only. The byte-parity test suite catches any regression.

### Phase 2: migrate cost class A mechanisms to read from the index (3-5 days)

60-80 mechanisms become O(1) lookups on the index. This is where most of the perf win lives. Per-mechanism PR. Each PR asserts byte parity on `to_dict()`. Each PR includes a wall-clock assertion that the migrated mechanism is at least 5x faster on the arXiv fixture.

### Phase 3: migrate cost class B mechanisms (5-7 days)

Indexed content walks. Each mechanism reads spans, fonts, or annotations from the index instead of re-walking the document. This is the second-largest perf win. Per-mechanism PR with byte-parity assertion.

### Phase 4: introduce early termination at the pass-1 boundary (1-2 days)

After pass 1, if any tier 1 or tier 2 finding is present, optionally return early. Behind a feature flag `early_termination=False` by default to preserve the full diagnostic shape during validation. Once validated, flag flips to `True` for the production `/scan` endpoint and stays `False` for the forensic suite. Users can request forensic mode explicitly via a query parameter.

### Phase 5: spatial indexing for class C, single re-parse for class D (3-5 days)

R-tree or grid for `overlapping_text` so cross-correlation is bounded by neighbors rather than pairwise. Single re-parse pass shared across all class D mechanisms. Per-mechanism PR with byte-parity assertion.

### Phase 6: horizontal-scale primitives (parallel to phases 1-5, 5-7 days)

Phase 6 ships the primitive that lets v1.1.4 demo a cluster end-to-end. Production-grade operational maturity (lifecycle policies, multi-region failover, periodic health monitoring, push notifications) is v1.1.5 work. The narrowing keeps Phase 6 plausible at 5-7 days alongside Phases 1-5.

What ships in v1.1.4:

- **Worker pool.** Process-per-worker, configurable concurrency, recycle every N scans (default N=100; per-worker RSS budget with kill-and-respawn on overshoot).
- **Queue layer.** Redis + RQ, single-region. Idempotency key on file SHA-256 + scanner version.
- **Async API.** POST /scans, GET /scans/:id, POST /scans:batch. Polling-only; webhook callbacks deferred.
- **Result store.** Object storage (S3 bucket, no lifecycle policy in v1.1.4) plus DB index keyed on (SHA-256, scanner version, scan timestamp, verdict). Deduplication: same SHA-256 + same version returns cached IntegrityReport without re-scanning.
- **Drift register.** Startup-only fixture scan per worker. Each worker scans a known adversarial fixture at startup and asserts the verdict matches the pinned expected value; mismatch flags the worker out of the load-balancer pool. Periodic in-flight cadence deferred.

What is explicitly deferred to v1.1.5 (logged in section 10): result store lifecycle policy, multi-region queue, periodic drift-register health-check cadence, async API webhook callbacks. Each is a reasonable narrowing, named here so the v1.1.4 ship target stays plausible and the v1.1.5 scope is pre-registered honestly.

### Phase 7: closure (1 day)

Re-run the dense-PDF benchmark and the four-density-class perf regression suite. Generate the v1.1.4 REPORT.md with measured numbers against pre-registered SLAs. Update README. Pre-register v1.1.5 deliverables.

**Total: 21-30 days of focused work, parallelizable between Bilal, Perplexity Computer, and Claude co-work where phases 2 and 3 can run independently and phase 6 can run alongside any of phases 1-5.**

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Cost taxonomy mis-assignment causes Phase 2 mechanisms to slow down rather than speed up | Phase 0 validates the taxonomy on the arXiv profile before any migration; Phase 2 per-mechanism PRs assert ≥5x speedup or revert |
| Byte-parity drift in the migration | Each per-mechanism PR runs the full byte-parity test suite; PR is blocked on green |
| ContentIndex build cost exceeds the savings on small documents | Index built lazily on first cost-class-B mechanism request; for documents that early-terminate at Pass 1, the index is never built |
| Worker memory leak across N scans | Worker recycle every N scans (configurable; default N=100); per-worker RSS budget with kill-and-respawn on overshoot |
| Pathological PDF blocks a worker | Hard timeout per scan (5 min forensic, 60s production); document marked scan_incomplete on timeout |
| Queue backlog under load spike | Backpressure on submission API; dynamic worker scaling (add workers when queue depth exceeds threshold) |
| Determinism drift between worker instances | Pinned dependencies in requirements.txt and pyproject.toml; drift register catches verdict divergence on known fixtures within minutes |
| Result store fills under sustained throughput | Tiered storage with lifecycle policy (hot 7d / warm 90d / cold archive); cost-bounded by retention policy |

## 10. Out of scope for v1.1.4

Logged for v1.1.5 or later, not folded into v1.1.4:

1. **Result store lifecycle policy.** v1.1.4 ships an S3 bucket with no tiered lifecycle. v1.1.5 adds hot-7d / warm-90d / cold-archive policy with the bucket-level cost-bound guarantee. Rationale: lifecycle config is straightforward but adds 1-2 days of setup time that is not load-bearing for the v1.1.4 demo.
2. **Multi-region queue.** v1.1.4 ships single-region Redis + RQ. v1.1.5 considers SQS or Cloudflare Queues for multi-region failover. Rationale: single-region is sufficient for the demo and most government batch ingest scenarios; multi-region is a v1.2 production-readiness concern.
3. **Periodic drift-register health checks.** v1.1.4 ships startup-only fixture scan per worker. v1.1.5 adds the every-N-minute in-flight cadence with worker auto-removal on verdict mismatch. Rationale: startup-only catches the most common drift modes (dependency skew, environment skew); periodic is needed to catch silent runtime corruption but adds operational complexity.
4. **Async API webhook callbacks.** v1.1.4 ships polling-only GET /scans/:id. v1.1.5 adds POST callback URL on scan completion. Rationale: polling covers most batch use cases; webhooks save bandwidth and latency for high-volume integrations but require retry logic and signature verification that is not load-bearing for v1.1.4.
5. **ML-based explanation layer.** v1.1.4 ships template-based explanation on the cold path; v1.3 adds LLM-driven explanation. Rationale: template explanations are deterministic and adequate for forensic operators; LLM explanations are a UX improvement, not a correctness requirement.
6. **Multi-tenant isolation.** v2.0 enterprise API.
7. **Auth / rate limiting / SLA contracts.** v2.0.
8. **Cross-document correlation at corpus scale.** Currently per-document; corpus-scale correlation is a different problem class.
9. **Custom mechanism authoring API.** Currently registry is closed; opening it is a separate decision.
10. **Mobile or edge deployment.** Cluster is server-side; edge deployment is a different scaling axis.

## 11. Architectural correspondence (parallel observation, not engineering derivation)

The cross-text observations the team has worked on — Hurst exponents on the Quranic structural chain, Fibonacci patterns across the corpora — describe verification systems whose property of interest is constancy across volume. More material reinforces the structure rather than overwhelming the verifier.

The stateless worker pool pays the registration cost once per cluster. The drift register catches divergence the moment it appears. None of these properties depend on the cross-text findings being correct in any specific empirical sense; they are textbook distributed-systems engineering. But a reader who finds the cross-text observations meaningful will see the same shape repeated here, and that observation is offered as a parallel rather than as a derivation.

The engineering stands on engineering merit. The architectural correspondence is for those who want it.
