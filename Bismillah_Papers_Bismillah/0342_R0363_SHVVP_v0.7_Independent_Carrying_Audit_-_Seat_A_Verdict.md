# SHVVP v0.7 Independent Carrying Audit - Seat A Verdict

**Auditor:** GPT-class / OpenAI-family independent carrying seat
**Seat:** A

## 1. Executive determination

The dispatch and nested release packet are authentic to every supplied SHA-256
receipt. The supplied rule suite reports **37 checks, 0 failures**, and the supplied
release verifier reports **8 gates, 0 failed**. The 59-page flagship PDF is openable,
not encrypted, completely renderable, free of blank or all-black pages, and legible
at the operational Section 8 tables. The empirical anchors, route-level inference
withdrawal, Phase C safety boundary, route scope limits, current-version identity,
and omission-to-`OUT OF SCOPE` correction were independently rechecked and are
materially preserved.

The release nevertheless **does not pass**. Two independently executed attacks show
that the core F-P6-1 trust-boundary defect remains open in relocated forms.

First, the normative manifest hashes one fixed committing-authority public key, but
`route_claims(..., trusted_pubkey=...)` permits the evaluator caller to substitute any
other public key. The verifier then authenticates commitments against that caller-
selected key without requiring equality to the key inside the manifest whose digest
is returned as `MANIFEST_SHA256`. I generated a new key, self-signed favorable R5-A
and R5-C subset commitments after outcomes, passed that key as `trusted_pubkey`, and
obtained `SUPPORTED-DESCRIPTIVE` for R5. The same commitments are rejected under the
actual manifest-bound key. Thus the result is not authenticated against the frozen
trust root represented by the reported manifest digest.

Second, the source promises a two-stage REALIZED commitment: a pre-run commitment to
the run identifier, log schema, initial chain value, and manifest, followed by a
signed close receipt. The code implements only the second stage. A finished Python
list can be assembled after outcomes, hash-chained from a deterministic genesis,
and signed as a close receipt. There is no pre-run commitment object, no linkage to
one, no independently fixed log schema or genesis, and no external or incremental
append-only receipt proving that the supplied list contains every qualifying event.
I constructed a favorable 50-event R2-B list after outcomes, signed its close
receipt, and obtained `SUPPORTED-DESCRIPTIVE`. The hash chain proves only that the
list was unchanged after the receipt was made; it does not prove that the list was
fixed or exhaustive before outcome selection.

Both defects permit the party controlling the evaluation inputs to define the
purported authoritative universe after seeing results. Because v0.7 exists
specifically to close that escape hatch, both are **HIGH and BLOCKING**.

### 3.1 Manifest-authority substitution

The frozen module reports this manifest-bound reference key:

```text
3b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29
```

The independent attack generated this different key:

```text

```

The attack then created post-outcome R5-A and R5-C commitments declaring only the
favorable minimum subsets as the complete sealed universes, signed them with the
new key, and called `route_claims` with that same key as `trusted_pubkey`.

Observed result:

```text
KEYS_EQUAL= False
DEFAULT_KEY_RESULT=REJECTED
OVERRIDE_RESULT_R5= SUPPORTED-DESCRIPTIVE
MANIFEST_SHA256= 667753069e360da59f7e3ac68c4bd2f6eef86896aa94f77e56d843babc5e3eab

```

The reported `MANIFEST_SHA256` did not change when the authority key was replaced at
runtime, even though the module states that the manifest digest binds the committing
authority. The output instead reports the caller-selected key. The result therefore
combines a digest bound to one trust root with commitments verified under another.

### 3.2 Post-outcome REALIZED log construction

The second attack constructed a contiguous 50-event R2-B list after outcomes,
computed the module's deterministic hash chain, signed a run-close receipt, and
supplied a raw record whose `commitment_id` was deliberately unrelated to any signed

Observed result:

```text

R2B_COMMITMENT_ID_RAW= does-not-match-any-receipt-id
```

The evaluator verified the self-consistency of the completed list and receipt, but
there was no pre-run commitment to verify. The signed `committed_at` string is not
semantically validated and is not an independent timestamp. No mechanism proves

run.

## 4. Findings

## F-P7-1

- **ID:** F-P7-1
- **SEVERITY:** **HIGH - BLOCKING**
- **LOCUS BY CONTRACT SECTION:** Sections 0.1 and 8.1b, especially “Frozen
  authority”; Section 8.4 execution contract; `shvvp_v0_7_route_gates.py` lines
  290-310 (`_manifest_canonical` and `MANIFEST_SHA256`), lines 416-433 (`_pubkey`
  and `_verify_sig`), lines 455-486 (commitment verification), and lines 766-881
  (`route_claims`); README “The commitment channel, for the auditor”; dispatch
  Section 4; producer tests and verifier wherever an ephemeral key is passed as
  `trusted_pubkey`.
- **SUBSTANCE:** The manifest canonicalization freezes
  `COMMITMENT_AUTHORITY_PUBKEY`, and `MANIFEST_SHA256` is computed from that frozen
  envelope. But `_pubkey(trusted_pubkey)` unconditionally prefers any nonempty
  runtime key, and `route_claims` passes it to every signature verification without
  checking that it equals the manifest-bound key. The return object then reports the
  override key while retaining the unchanged digest of the different frozen key.
  The interface therefore authenticates the claimant-selected commitment under a
  claimant-selected trust root. The prose assertion that Channel A is “authenticated
  against the committing-authority public key frozen in the scope manifest” is
  false for the executable override path. The sentence that the reference key is
  “replaced by the production custodian key at seal time” is also incompatible with
  retaining the already frozen manifest digest: replacing the key must produce a
  new canonical manifest and digest, whereas the runtime override does not. The
  independent call used a non-manifest key to self-sign favorable post-outcome R5
  subsets and returned `SUPPORTED-DESCRIPTIVE`.
- **DISPOSITION:** Freeze a successor version in which the normative evaluator
  verifies only against the exact public key inside the canonical manifest. Remove
  `trusted_pubkey` from the public route interface, or reject unless it is byte-for-
  byte equal to the manifest-bound key. If a production custodian key differs from
  the reference key, substitute it **before the new contract is frozen**, regenerate
  the canonical manifest digest, source, PDF, packet manifests, and every dependent
  receipt, and dispatch that new identity. Do not permit the evaluation call to
  establish its own trust root. Add a decisive regression: a commitment signed by a
  key that equals the supplied override but differs from the manifest-bound key must
  be rejected before any universe cardinality or share is computed.
- **CROSS-REFERENCE:** Round-6 F-P6-1; Section 8.1b statements that the authority is
  frozen and folded into `MANIFEST_SHA256`; amendment/adjudication entry A-7.1;
  producer test A10, which proves only that the default key rejects the ephemeral
  fixture but then bypasses that default for the positive path.

## F-P7-2

- **ID:** F-P7-2
- **SEVERITY:** **HIGH - BLOCKING**
- **LOCUS BY CONTRACT SECTION:** Section 8.1b “Frozen REALIZED commitment”; Section
  8.4 execution contract; `shvvp_v0_7_route_gates.py` lines 372-406
  (`run_close_payload` and `run_log_chain`) and lines 474-522
  (`verify_realized_commitment`); producer tests B1-B9 and verifier gate G3.
- **SUBSTANCE:** Section 8.1b freezes a two-stage design. Before the run, a run
  commitment must fix the run identifier, log schema, initial chain value, and
  manifest digest. The code defines no pre-run commitment payload, accepts no such
  object, verifies no pre-run signature or immutable receipt, and does not bind the
  close receipt to one. `run_log_chain` derives its genesis at evaluation time from
  the caller-supplied `run_id` and the module manifest. The only authenticated
  object is a close receipt over a list already assembled in memory. This detects
  changes made after that receipt, but cannot detect events omitted before the list
  was closed or prove that the list was append-only while the run occurred. An
  authorized or caller-selected signer can inspect outcomes, construct a favorable
  subset, generate its chain and close receipt, and obtain the authoritative
  denominator. The independent 50-event R2-B construction did exactly that and
  returned `SUPPORTED-DESCRIPTIVE`.
- **DISPOSITION:** Implement the promised first stage as a separately authenticated,
  pre-run commitment containing at minimum a unique commitment ID, run ID,
  component, universe ID, protocol version, manifest digest, event/log schema digest,
  inclusion rule, genesis or initial chain value, authority, and an independently
  verifiable pre-run sequence or timestamp. The close receipt must include and sign
  that commitment ID and digest. Verification must reconstruct the log from an
  immutable external record or individually authenticated append events, not merely
  accept a completed caller-provided list. Add regressions in which a favorable list
  and close receipt are created after outcomes under the otherwise valid authority;
  they must be rejected when no valid pre-run commitment and append history exist.
- **CROSS-REFERENCE:** Round-6 F-P6-1 disposition for authoritative append-only run
  logs; Section 8.1b’s express “committed in two stages” promise; amendment A-7.1;
  tests B1-B9, which establish post-close integrity only.

## F-P7-3

- **ID:** F-P7-3
- **SEVERITY:** **MEDIUM**
- **LOCUS BY CONTRACT SECTION:** Sections 8.1b and 8.4, which define
  `commitment_id` as Channel B’s sole reference to Channel A;
  `shvvp_v0_7_route_gates.py` lines 312-320 (`_BIND_BY_KIND`), commitment payloads
  at lines 353-388, and `route_claims` lines 801-803.
- **SUBSTANCE:** A SEALED or REALIZED raw record must contain a nonempty
  `commitment_id`, but the value is never read after syntactic validation. The
  commitment payloads contain no `commitment_id`; commitments are selected only by
  `commitments.get(component_key)`. A raw record stating
  `does-not-match-any-receipt-id` is accepted and can produce
  `SUPPORTED-DESCRIPTIVE`. Component, universe, version, and manifest binding still
  prevent several replay classes, so this is not independently the carrying block.
  It nevertheless contradicts the frozen two-channel contract and makes the claimed
  reference unauditable.
- **DISPOSITION:** Put a unique `commitment_id` inside every signed sealed,
  pre-run, and close payload. Key or index the authoritative commitment bundle by
  that ID, require the raw record’s ID to resolve exactly to the signed object, bind
  close receipts to the pre-run commitment ID, and reject duplicate, unknown,
  component-mismatched, or reused IDs. Add a regression using an arbitrary nonempty
  raw `commitment_id`; it must reject.
- **CROSS-REFERENCE:** Section 8.1b “Two channels, frozen”; Section 8.4 “Sole
  admissible input”; F-P7-2’s required pre-run-to-close linkage.

  denominator, rather than relying only on stale-version phrase scans.

## 5. Four-axis assessment

### 5.1 Falsifier integrity

**FAILED.** v0.7 closes direct cardinality and hash smuggling from Channel B and
correctly rejects many mutation and replay attacks. It does not close authority
selection or pre-run completeness. A caller-selected key can authenticate a
caller-defined universe while the evaluator still reports the digest of another
frozen key, and a post-outcome list can be signed as the complete realized log with
no prior commitment. F-P7-1 and F-P7-2 are dispositive.

### 5.2 Empirical-anchor integrity

**PASSED.** The official primary records independently support the protocol’s narrow
anchor treatment:

- Anthropic’s Mythos Preview report attributes the FreeBSD NFS exploit to a
  17-year-old flaw, describes a 20-gadget chain split over multiple packets, and in
  the detailed account describes a chain over 1,000 bytes split into six sequential
  RPC requests. The protocol preserves both descriptions as attributed capability
  profiles rather than treating them as protocol ground truth.
- The FreeBSD advisory contains the authentication tension recorded by the protocol:
  the problem description says prior client authentication is not required, while
  the impact paragraph describes an authenticated user able to send packets to the
  NFS server while `kgssapi.ko` is loaded. `UNKNOWN-CONTESTED` is a faithful status.
- The UK AI Security Institute reports the 32-step range, 3 of 10 complete attempts,
  average progress of 22 steps versus 16 for the next-best model, runs up to a
  100-million-token budget, and limitations including absent active defenders and
  defensive tooling. The protocol preserves those limitations and uses the result
  only as a motivating capability profile.

Primary records checked:

- [Anthropic, Assessing Claude Mythos Preview's cybersecurity capabilities](https://www.anthropic.com/research/mythos-preview)
- [FreeBSD-SA-26:08.rpcsec_gss](https://www.freebsd.org/security/advisories/FreeBSD-SA-26:08.rpcsec_gss.asc)
- [UK AI Security Institute, Our evaluation of Claude Mythos Preview's cyber capabilities](https://www.aisi.gov.uk/blog/our-evaluation-of-claude-mythos-previews-cyber-capabilities)

### 5.3 Internal consistency

**FAILED.** The source says the manifest-bound authority is frozen, while the code
accepts a different runtime authority without changing the manifest digest. The
source promises a two-stage realized commitment, while the code implements only the
close stage. The source says `commitment_id` references an authenticated object,
while the code ignores its value. Table 8.2a also says a sealed cardinality is
carried on the record, contradicting the Channel A-only rule. Route-level inference
withdrawal and current v0.7 identity remain internally consistent.

### 5.4 Scope honesty

**FAILED at the executable evidence boundary; passed in the prose claim language.**
The protocol still prohibits the aggregate claim that “SHV is validated,” limits
all route outputs to `SUPPORTED-DESCRIPTIVE`, and associates every supported
statement with a same-context scope limit. But the executable label may be based on
a universe authenticated under a non-manifest trust root or on a realized list first
committed after outcome selection. The resulting scope can therefore be narrower and
more favorable than the purported committed universe.

## 6. Safety-boundary determination

**PASSED.** Phase C remains restricted to offline containers, private synthetic
vulnerabilities, non-deployable proofs, and controlled access. The source declares
this boundary non-amendable and any weakening amendment void. No later clause
creates a live-target or deployable-exploit path.

## 7. Withdrawn-inference determination

**PASSED.** The normative route path contains no p-value, null hypothesis,

generalization. All components remain descriptive Class G gates, and no route output
can exceed `SUPPORTED-DESCRIPTIVE`. The blocking findings concern authenticity and
completeness of the evidence universe, not reintroduction of statistical inference.

## 8. F-P6-2 closure determination

remaining Table 8.2a contradiction concerns the source of the sealed cardinality,
not a superseded current-version label.

## 9. Limits of this audit

This audit does not certify future execution, empirical validity, universal
correctness, external validity, or safety beyond the frozen contract. No empirical
result is certified here. The audit did verify byte custody; execute the supplied
rule suite and verifier; construct independent adversarial calls against the
normative gate; inspect the relevant source-code paths; render and visually inspect
the complete flagship PDF; verify current-version parity; and recheck the required
external anchors against official primary records.
