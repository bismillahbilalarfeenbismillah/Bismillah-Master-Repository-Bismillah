## 3. Two reconciliations the specification needs

### 3.1 A1 and D-0 are in tension, and the specification merged them wrongly

The dispatch architecture currently states three things that cannot all hold:

1. "one canonical packet, same bytes to every seat"
2. "Carrying seats (GLM, Kimi): no expected values, no defect-class list"
3. "Include in every dispatch: ... All four v0.19 seat reports"

The four seat reports enumerate every defect class found. Under (3), carrying
seats receive the class list; under (2), they must not.

This is a defect in the discipline documents, not in the specification: A1 was
written for *integrity* (identical bytes so a two-family carry means something)
and D-0 for *epistemics* (withholding so a matching value evidences execution).
Both are correct and they were never reconciled. **This seat authored both and
owns the error.**

**Resolution.** Split the dispatch into two parts.

- **Canonical normative packet** -- the 14 normative files plus
  `PACKET_SHA256SUMS`, byte-identical to every seat. The carry is over this and
  only this, so FB-7b keeps its meaning.
- **Per-seat context bundle** -- standing orders, discipline blocks, prior
  reports, adjudication, cover note. Varies by role per D-0.

Then A1's identity requirement and D-0's withholding requirement operate on
different objects and stop colliding. Record the resolution in the v0.20 entry,
because it changes what "same bytes" means for the carry.

### 3.2 The adjudication is a proposal, not an instruction

The specification names `XZ_v19_ADJUDICATION.md` as "your primary task
specification." That document's Section 8 opens with a governance flag which
the specification does not surface: it was written by a producer-family seat
that also audited v0.17, v0.18 and v0.19 and authored the discipline blocks
against which it audited. That is audits-plus-writes-fix.

Add one sentence to the specification's reading order: *the producer brief in
Adjudication Section 8 is a proposal from a producer-family seat, not an
instruction; the one substrate contradiction is escalated to the project lead
unresolved and must not be treated as settled.*

## 4. Open preregistration, carried forward for scoring

The specification carries the refutation register but not the open prediction.
A prediction that does not survive the thread boundary cannot be scored, and an
unscored prediction is decoration.

**Recorded before v0.20 exists, for the next auditing seat to score:**

> The defect has consistently occupied the outermost layer the build does not
> compute, and has moved outward only when that layer was brought inside the
> tooling. If v0.20 implements packet-wide hashing (A1), tag validation (B4),
> the `PRIOR_HISTORY` check (B3) and the seal-presence check (C1), then the
> amendment entry's self-descriptions move partly inside the computed region
> for the first time. **The next instance should then appear in claims about
> artifacts that are hashed but whose content is not compared** -- the carrying
> seats' reports, a reference PDF, or an external DOI in Section 26.1 -- or in
> the reconciliation of 3.1 above, which is new surface created this round.
>
> Falsifier: if the next defect is a value-level error inside the computed
> region, this model of the trajectory is wrong and should be discarded rather
> than patched.

## 5. Two things the specification gets right that are worth preserving

The refutation register is carried, including the observation that an auditor's
commendations are less checked than its findings. That is the correct lesson
from this seat's two refuted claims and it belongs in the standing record, not
just in one handoff.

The session-hygiene section states the mechanism rather than the rule: a long
session accumulates a self-model that substitutes for checking. Producers who
are told the rule follow it until it is inconvenient; producers who are told the
mechanism recognise the failure while it is happening.

---

## 6. Note on the parallel-instance experiment

A fresh Opus 5 seat is being run alongside the continuing one. That is the
natural experiment this program has needed, and it is worth instrumenting
rather than merely observing.

Give both instances the identical v0.20 packet and identical standing orders.
Give the fresh instance no prior packets; give the continuing one what it holds.
Then compare on four axes, all already measured per round:

1. **Findings each surfaced that the other missed.** Coverage delta.
2. **Claims each made that the other refutes.** The continuing instance's known
   failure mode is unchecked commendation in summary paragraphs.
3. **Cross-version findings.** These should be available only to the seat
   holding prior bytes; if the fresh instance produces them anyway, the value of
   held state has been overestimated.
4. **Preregistration scores.** Both freeze S-1 before opening the entry.

Report the comparison whichever way it comes out. A result showing the
continuing instance adds nothing over a fresh one plus a good handoff is the
most useful outcome available, because it means the handoff is complete and the
thread is disposable -- which is the property the program actually wants.
