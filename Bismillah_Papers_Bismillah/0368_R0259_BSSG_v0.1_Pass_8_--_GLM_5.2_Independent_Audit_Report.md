## 4. Findings

### GLM-P8-01 -- Commit-time fresh witness WithinAuth assessment not revalidated

1. **ID:** GLM-P8-01
2. **Location:** `bssg_gate.py` lines 1382-1423, `_commit_after_reserve` method, commit-time fresh witness check
3. **Claim/Observation:** The authorization-time `_witness_healthy` function (lines 962-971) requires `within_auth_assessment.value == "outside_subject_authority"` -- if the witness declares the evidence is within the subject's authority, authorization returns UNKNOWN with `E-WITHINAUTH-NOT-ESTABLISHED`. However, the commit-time fresh witness check (lines 1382-1423) does NOT revalidate this field at all. The commit-time check verifies health, signature, epoch equality, witness_id, covered_subject, independence_declaration, sequence, expiry, and coverage -- but omits the WithinAuth assessment. A fresh witness at commit time declaring `within_auth_assessment.value = "within_subject_authority"` still commits successfully. Probe DP-G3a confirms: `outcome=COMMITTED_PENDING_OUTCOME, reasons=[]`.
4. **Severity:** MAJOR
5. **Evidence:** Probe DP-G3a output: `FAIL DP-G3a [MAJOR] commit-time fresh witness WithinAuth assessment IS revalidated  outcome=COMMITTED_PENDING_OUTCOME reasons=[]`. Code at line 969 checks `assessment.get("value") != "outside_subject_authority"` at authorization time; the commit-time block at lines 1382-1423 has no equivalent check.
6. **Required repair:** After the independence_declaration check at line 1411, add a WithinAuth revalidation: verify `fresh.get("within_auth_assessment", {}).get("value") == "outside_subject_authority"`, returning `E-COMMIT-WITNESS-WITHINAUTH-NOT-ESTABLISHED` on failure. This closes the gap where a fresh witness could override the authorization-time WithinAuth assessment.

### GLM-P8-02 -- Commit-time fresh witness observed_at not revalidated

1. **ID:** GLM-P8-02
2. **Location:** `bssg_gate.py` lines 1382-1423, `_commit_after_reserve` method, commit-time fresh witness check
3. **Claim/Observation:** The authorization-time `_witness_healthy` function (line 951) checks `observed_at > now + self.max_skew` and returns UNKNOWN with `E-WITNESS-CLOCK-AMBIGUOUS` if the witness timestamp is too far in the future. The commit-time fresh witness check does NOT verify `observed_at` at all -- it only checks `expires_at` (lines 1417-1420). A fresh witness with `observed_at = "2030-01-01T00:00:00Z"` (far future, clock-ambiguous) still commits successfully. Probe DP-G3b confirms: `outcome=COMMITTED_PENDING_OUTCOME, reasons=[]`.
4. **Severity:** MAJOR
5. **Evidence:** Probe DP-G3b output: `FAIL DP-G3b [MAJOR] commit-time fresh witness observed_at IS revalidated (clock ambiguity)  outcome=COMMITTED_PENDING_OUTCOME reasons=[]`. Code at line 951 checks clock ambiguity at authorization time; the commit-time block at lines 1382-1423 has no equivalent check for `observed_at`.
6. **Required repair:** After the expiry check at line 1420, add an `observed_at` revalidation: parse `fresh.get("observed_at")`, verify it is not None and `observed_at <= now + self.max_skew`, returning `E-COMMIT-WITNESS-CLOCK-AMBIGUOUS` on failure. This closes the gap where a fresh witness could carry a future-timestamped observation that bypasses the clock-ambiguity check.

### GLM-P8-03 -- Root-directory target over-rejection

1. **ID:** GLM-P8-03
2. **Location:** `bssg_gate.py` line 576, `canonical_target` function
3. **Claim/Observation:** The trailing-slash detection `trailing_slash = len(segments) > 1 and segments[-1] == ""` requires at least 2 segments. For a root-directory target like `bssg://host/`, the path produces `segments = ['']` (one empty segment), so `len(segments) > 1` is False, `trailing_slash` is False, and the empty segment triggers `return None` at line 581. The spec (section 11) says "a single trailing slash (directory target) canonicalizes." A root directory is a valid directory target, but the code refuses it. Probe DP-G1a confirms: `canonical=None`.
4. **Severity:** MINOR
5. **Evidence:** Probe DP-G1a output: `FAIL DP-G1a [MINOR] root-directory target canonicalizes (single trailing slash)  canonical=None`. Control probe DP-G1d confirms that `https://db.example.internal/records/` (2+ segments) canonicalizes correctly.
6. **Required repair:** Change the trailing-slash condition to `len(segments) >= 1 and segments[-1] == ""` and handle the root-directory case (path = `/`) by returning `scheme://host/` without requiring additional path segments.

### GLM-P8-04 -- Percent-encoding over-rejection

1. **ID:** GLM-P8-04
2. **Location:** `bssg_gate.py` line 568, `canonical_target` function
3. **Claim/Observation:** The code refuses ALL percent-encoding with `if "%" in rest: return None`. The spec (section 11) says "percent-encoded separators" are uncanonicalizable -- meaning percent-encoded `/`, `@`, `:`, or other separator characters that could change the structure of the target. The code's blanket refusal also rejects non-separator percent-encoded characters like `%2D` (hyphen), `%41` (letter A), or `%30` (digit 0), which are structurally unambiguous. Probe DP-G1b confirms: `canonical=None` for a target containing `%2D`.
4. **Severity:** MINOR
5. **Evidence:** Probe DP-G1b output: `FAIL DP-G1b [MINOR] percent-encoded non-separator (%2D hyphen) target canonicalizes  canonical=None`. Code at line 568: `if "%" in rest: return None`.
6. **Required repair:** Replace the blanket refusal with a targeted check: refuse only percent-encoded separator characters (`%2F`, `%2f`, `%40`, `%3A`, `%3a`, `%23`, `%3F`, `%3f`) that could alter the target's structural interpretation. Alternatively, decode percent-encoding and re-validate the decoded form against the canonical character set.

### GLM-P8-05 -- @ in path segment over-rejection

1. **ID:** GLM-P8-05
2. **Location:** `bssg_gate.py` line 570, `canonical_target` function
3. **Claim/Observation:** The code refuses ALL `@` in the raw target string with `if "@" in rest: return None`. This is intended to reject embedded credentials (`user:pass@host`), but it also rejects `@` appearing in a path segment (e.g., `https://db.example.internal/records/user@domain`), which is a valid path character per RFC 3986. Probe DP-G1c confirms: `canonical=None`.
4. **Severity:** MINOR
5. **Evidence:** Probe DP-G1c output: `FAIL DP-G1c [MINOR] @ in path segment (not credentials) canonicalizes  canonical=None`.
6. **Required repair:** Only refuse `@` if it appears before the first `/` in the path (i.e., in the authority component). After the first `/`, `@` is a valid path character and should not be rejected.

### GLM-P8-06 -- Unicode/IDNA normalization gap

1. **ID:** GLM-P8-06
2. **Location:** `bssg_gate.py` `canonical_target` function, authority lowercasing (line ~563)
3. **Claim/Observation:** The canonical_target function lowercases the authority component but does not perform IDNA normalization. Two representations of the same internationalized domain name -- Unicode form (`bücher.example`) and Punycode/ACE form (`xn--bcher-kva.example`) -- canonicalize to different targets. A scope declared in one form will not match a target in the other. Additionally, Unicode homoglyph authorities (Latin `b` vs Cyrillic `в`) canonicalize to different targets, which is not a scope escape but a normalization gap. Probes DP-G2a and DP-G2d confirm.
4. **Severity:** MINOR
5. **Evidence:** Probe DP-G2a: `latin=https://db.example.internal/records/row-1 cyrillic=https://dв.example.internal/records/row-1` (different). Probe DP-G2d: `unicode=https://bücher.example/records/ punycode=https://xn--bcher-kva.example/records/` (different).
6. **Required repair:** Apply IDNA normalization to the authority component (e.g., `authority.encode('idna').decode('ascii')`) so that Unicode and Punycode forms canonicalize to the same target. Document that homoglyph detection is out of scope for v0.1 (it requires a confusable-character table).

### GLM-P8-07 -- Verifier prohibited-phrase coverage gap

1. **ID:** GLM-P8-07
2. **Location:** `verify_bssg_v0_1.py` lines 63-76, `PROHIBITED_PATTERNS` list
3. **Claim/Observation:** The spec (section 1.3, item 8) prohibits "BSSG preserves capability" without the conditional "under evidence-plane health." The verifier's `PROHIBITED_PATTERNS` list does NOT include `r"preserves capability"`. The verifier scans for 13 patterns, but spec item 8 is missing. The verifier correctly scans for "is validated" (item 5), "guarantees safety" (item 5), and all other prohibited phrases. No actual prohibited claim exists in the package -- the spec itself uses "preserves capability under evidence-plane health" with the required conditional (spec line 667). ## 5. Standing Non-Defects Judgment

### D.2 -- Monotone health-narrowing

**Verdict: CORRECTLY IMPLEMENTED. No defect.**

The `_apply_narrowing` function (lines 1258-1283) implements three checks:
1. **Widening terminal:** If `not new_ceiling <= previous` (new ceiling is not a subset), the session terminates with `E-AUTHORITY-WIDENING` (line 1268-1270). Correct.
2. **Non-strict narrowing terminal:** If health drops (`HEALTH_ORDER[health] < HEALTH_ORDER[previous_health]`) and the prior ceiling is non-empty and the new ceiling is not a strict subset (`not (new_ceiling < previous)`), the session terminates with `E-NONSTRICT-NARROWING` (lines 1271-1278). Correct -- a health drop must be accompanied by strict narrowing.
3. **Epoch advance:** If the ceiling or health changed, the authority epoch is incremented (line 1279-1280). Correct.

Recovery (DEGRADED -> HEALTHY) correctly triggers the widening terminal: the HEALTHY ceiling is typically a superset of the DEGRADED ceiling, so `not new_ceiling <= previous` is True. This is the intended behavior -- recovery is a widening event that requires an amendment, not an automatic narrowing. Consistent with spec section 8.

### D2 -- Witness-epoch monotonicity

**Verdict: CORRECTLY IMPLEMENTED. No defect.**

The `_witness_healthy` function (lines 941-946) checks epoch and sequence monotonicity per `witness_id`:
- Epoch rollback (`epoch < prior_epoch`) -> FALSE with `E-WITNESS-EPOCH-ROLLBACK` (line 942-943). Correct.
- Same epoch, lower sequence (`epoch == prior_epoch and sequence < prior_sequence`) -> FALSE with `E-WITNESS-SEQUENCE-ROLLBACK` (line 944-946). Correct.
- New epoch resets the sequence check (the `prior_sequence` is only compared when `epoch == prior_epoch`). Correct.

The highest-seen epochs and sequences only advance when BOTH `WitnessHealthy == TRUE` and `EvidenceCurrent == TRUE` (lines 1162-1170). This ensures that a stale or unhealthy witness does not poison the monotonicity state. Correct.

### AMEND_AUTHORITY scope

**Verdict: CORRECTLY IMPLEMENTED. No defect.**

The `submit_amendment` function (lines 1557-1561) refuses `AMEND_AUTHORITY` corrections with `E-AMENDMENT-CLASS-UNIMPLEMENTED`. The correction-event schema admits `AMEND_AUTHORITY` in the enum (it is a valid value), but the code refuses it with a distinct, honest error code. The code checks signature validity and schema validity before the class check (lines 1534-1556), which is defensible ordering: a structurally invalid amendment should be rejected before the class-specific logic. The spec (R-1) marks AMEND_AUTHORITY as reserved for a future version. The attack register AT-18 confirms: "Self-amendment or single-party recovery" is "ENFORCED structurally, ASSUMED semantically." Consistent with spec R-1.

**Producer agreement:** I agree with the producer on all three standing non-defects. D.2, D2, and AMEND_AUTHORITY are all correctly implemented and correctly classified as non-defects.
